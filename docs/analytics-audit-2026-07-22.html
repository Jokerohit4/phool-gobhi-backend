01

The honest picture

The architecture (facade → Postgres, vendor-neutral, cheap) is genuinely good design and it's real, not aspirational — I queried it directly. But three things are true at once: it only runs in dev, the docs describe an event dictionary that's already drifted from what's shipped, and the one funnel that matters most for the Aug 1 launch — partner onboarding — isn't actually landing data.

Dark Production emits nothing

Checked all six *-prod Cloud Run services directly: none have ANALYTICS_PROVIDER set at all — not even none explicitly, it's just absent. Every one of the 366 rows below is dev-environment testing traffic. There is currently no way to answer any real question about real users, because none has ever been asked to report anything.

Silent Partner-app client events aren't reaching the table

The partner app's own analytics code (onboarding_started, onboarding_step_completed, screen views) is written, wired through DI, and looks correct on read. But querying properties->>'app' on every client-sourced row in dev: 98 are tagged phool_gobhi (the customer app) and 0 are tagged phool_gobhi_partner. The default sink is console in debug builds and only switches to the first-party HTTP sink in release — so unless someone has specifically run a release-mode partner build against the dev gateway, every onboarding tap has only ever been printed to a debug log and discarded. The only partner-onboarding signal that exists today is the server-side truth events (gym_created/gym_approved), which start mid-funnel — step 1–2 drop-off is invisible.

Drifted The event dictionary in docs/ANALYTICS.md is missing 12 shipped events

Diffing the doc against actual track() call sites turns up a full second product surface the doc never mentions — all six buddy_* events, plus gym_rejected, attendance_verified (fired from two different check-in paths), staff_account_created/revoked, and partner_payout_recorded. None of this is wrong, exactly — it's just that nobody would know to query for it from reading the doc alone.

Broke today A funnel was renamed out from under itself this afternoon

Commit b8c7251 ("...subscriptions wallet-only...", 2026-07-22 18:38 IST) removed the two-step Razorpay subscription flow (subscription_order_created → subscription_purchased) in favor of a single wallet-debit step, now emitted as subscription_purchased_wallet. The dev table still holds the old names — 13 subscription_order_created and 4 subscription_purchased rows through Jul 20–22 — with no successor rows yet under the new name. This is the exact failure mode the doc's own naming rule warns about ("renaming a shipped event breaks historical funnels"), caught in the act rather than after the fact.

git log -p -S "subscription_order_created" services/wallet-service → b8c7251 replaces createSubscriptionOrder (Razorpay order + track('subscription_order_created', …)) with purchaseSubscriptionWithWalletHandler (direct debit + track('subscription_purchased_wallet', …))

Open door POST /api/events has no allowlist, auth, or rate limit

It's a deliberately public route (client events pre-login must reach it), scoped to a 128kb body cap — but it accepts any event name and any distinct_id, unauthenticated. Proof it's already being hand-poked: one row in dev carries distinct_id = 'verify-probe-1', clearly a manual curl test, sitting in the same table as real user rows with nothing to distinguish it programmatically. At real traffic this is also an unrate-limited write path into your primary shared Postgres.

Blind spot Website and admin portal have zero instrumentation

Grepped both repos for analytics, gtag, posthog, plausible, mixpanel, segment — nothing. The website now has real customer login/session/account pages (shipped 2026-07-20) and the admin portal drives gym approvals and payouts — both are currently completely dark to this pipeline. The gateway's /api/events route would take a web POST identically to a mobile one; nothing backend-side is customer-app-specific.

03

Funnels buildable today, as-is

No schema change needed for any of these — the JSONB shape already carries what's required. Each is annotated with what the live dev data actually shows, not just what's theoretically possible.

Activation

otp_requested→otp_submitted→signup_completed / login_completed
Fully wired, client + server, and verified stitching across the login boundary — I traced real anon_id → userId joins in the data (e.g. anon session → user 9, three screen views, one OTP request, one submit, all before identify). This funnel works exactly as designed today.

Conversion / GMV

gym_viewed→slot_selected→book_tapped→booking_confirmed ⤷ booking_failed
Live in dev: 20 views → 4 taps → 8 confirms (confirms exceed taps because client-side taps aren't landing as reliably as server-side confirms — same debug-vs-release sink issue as the partner app, just less severe). booking_failed already carries a reason field (slot_full / insufficient_balance) so the failure branch is breakdown-ready.

Fulfillment

booking_confirmed→checkin_requested→attendance_verified→booking_completed
Structurally sound and now richer than the doc describes: attendance_verified carries a method (qr_scan by partner, or qr_geofence_self for customer self-check-in) — a real no-show vs. attended vs. how-attended breakdown is possible, it's just not in the funnel definition anyone's looking at.

Supply (partner onboarding → approval)

onboarding_started→onboarding_step_completed ×4→gym_created→gym_approved/gym_rejected
Broken in practice, not in design — the first four steps are the partner-app client events that aren't reaching Postgres (§01). What is answerable today: gym approval SLA from the last two steps alone — 5 gyms created, 3 approved, 2 rejected, all within dev testing. The step-by-step onboarding drop-off — arguably the most decision-relevant funnel right now given gym supply is the actual launch bottleneck — has zero real signal.

Wallet

topup_tapped→wallet_topup_order_created→wallet_topup_succeeded ⤷ wallet_topup_failed
Complete, including the async Razorpay-webhook path (wallet_topup_succeeded carries via: 'webhook' when it lands out-of-band from the direct verify call) — a genuinely well-instrumented funnel.

Buddy engagement — not in the documented funnel list at all

buddy_profile_created→buddy_swiped→buddy_matched→buddy_message_sent
Fully instrumented server-side and already showing a real shape in dev: 12 profiles → 17 swipes → 6 matches → 6 messages (plus buddy_blocked and buddy_unmatched as negative-signal branches). Missing only the view step at the top — there's no client event for "buddy card shown," so swipe-through-rate against impressions can't be computed, only swipe-to-match rate.

Subscriptions — mid-migration as of today

subscription_order_created → subscription_purchased⟶subscription_purchased_wallet
Also absent from the documented funnel list. As of this afternoon's commit it's a single-step event (wallet-only purchase, no order/verify split) — treat the old two-step rows as historical only; any new query should key off subscription_purchased_wallet.
04

What you can and can't figure out today

Answerable right now

  • Signup vs. login mix, and role/user_type breakdown, for anyone who's touched dev
  • Booking drop-off shape and failure-reason mix (slot_full vs. insufficient_balance)
  • Gym approval turnaround time (gym_created → gym_approved timestamp delta)
  • Buddy swipe-to-match and match-to-message activation rates
  • Wallet top-up success rate, including async webhook completions
  • Cross-service journeys for one person — booking, wallet, and buddy activity are joinable today by distinct_id in one table, no warehouse needed

Not answerable yet

  • Anything about real users — there is no production data, full stop
  • Partner onboarding step drop-off — the client events don't land (§01)
  • Session length, DAU, bounce, or any time-boxed engagement metric — there's no session concept in the schema at all
  • Conversion by city end-to-end — city only appears on gym-side events; booking/wallet rows would need a join back to the gym table to slice by city
  • Pre-login attribution across app restarts — the anon id lives in memory only and resets on every cold start, so it can only stitch a single continuous session
  • App-version or OS-version cohorting — platform is captured (android/ios) but not app build number
05

Where to spend effort next

  1. Turn dev results into prod results.Six env vars (ANALYTICS_PROVIDER=postgres + a DB URL) across the five prod services and gateway, then /deploy <service> prod. This is the single highest-leverage change here — everything else in this doc is analysis of test data until this happens.
  2. Find out why partner-app events aren't landing.Confirm whether QA has ever run the partner app with --dart-define=ANALYTICS_PROVIDER=firstparty, or whether it's simply always tested in debug. If onboarding drop-off matters for the Aug 1 supply push, this is the fastest fix on the list — no new code, just a build flag.
  3. Put a floor under /api/events.An allowlist of known event names plus basic per-IP rate limiting closes the open door without touching the pre-login use case it exists for.
  4. Reconcile the doc.Fold in the 12 undocumented events (buddy suite, attendance methods, staff actions, payouts) and correct the subscription funnel to the new single-step shape — five minutes now, versus someone rediscovering this the hard way later.
  5. Give client rows a real service dimension.Every client event is tagged service = 'gateway' at the top level; the only way to tell customer-app from partner-app traffic apart is reaching into properties->>'app'. Promoting that to a first-class column (or at least a GIN index on properties) would make ad-hoc queries much less error-prone as volume grows.
  6. Put a read-only view on top of the SQL.Every number in this document came from hand-written queries run just now — there is no dashboard. The admin portal already exists and already has an internal audience; a page that runs the funnel queries in docs/ANALYTICS.md §8 would turn this from an occasional audit into something checked weekly.
